# mizuRoute knowledge pack

## What this model is

mizuRoute is a river-network routing model. It takes runoff already generated by a land or hydrological model and moves it down a network of reaches, optionally delaying it first with a hillslope unit hydrograph and optionally holding it in lakes and reservoirs. It solves no land physics of its own. Its signature is that the channel solution is a **choice**: five schemes — an impulse-response convolution, a Lagrangian and an Eulerian kinematic wave, Muskingum-Cunge and a diffusive wave — can be selected, or run side by side in one simulation, and a sixth option simply accumulates runoff without any transport at all.

## What this pack covers

Pinned to mizuRoute **tag `v3.1.1`, commit `28514dea`**. It covers the **standalone driver**: its control file, its network, runoff and mapping inputs, the five routing schemes and the accumulation option, hillslope routing, lakes, water balance, restart and the MPI decomposition; the coupled build is covered only where it differs. It does not cover any other release, any host's own configuration, or the numerical behaviour of the reservoir schemes. **No mizuRoute input or output data and no build exist here**, so every fact is read in the source, with control-file facts also confirmed against the two sample control files. No runtime cost is measured.

## How to use it — as a person

Start with [card.md](card.md): one page on what mizuRoute needs from upstream, the file kinds, how routing methods are selected, and what a value in an output record means. Then look up what you need by name, one real run, abridged only by `...`:

```
$ tools/hcm_lookup.py --pack mizuroute IRFroutedRunoff
# IRFroutedRunoff  [mizuRoute history output variable]
  units: m3/s
  value over the output interval (kind): interval_mean
  where: route/build/src/popMetadat.f90:241 ...
  CURATED OVERLAY (...): ... writes its DISCHARGE under the name 'volume' ...
```

When something looks wrong, go to [failures.md](failures.md) by symptom; before a total, a balance or a scheme comparison, read [recipes.md](recipes.md). Before a run, `tools/hcm_check.py check-control-file --pack mizuroute --file <control file>` names every tag the pinned parser does not recognise — including one copied from the documentation or from the shipped sample — and every value outside a catalogued accepted set, quoting the parser's own message; it is quiet on `SAMPLE-coupled.control` and fires on `SAMPLE.control`.

## How to use it — as an agent

Read [card.md](card.md) only. Resolve any control key, variable or parameter with `tools/hcm_lookup.py --pack mizuroute <NAME>` rather than reading a catalog. Then open [failures.md](failures.md) by symptom, [processes.md](processes.md) by process, or [recipes.md](recipes.md) by task. This README is not part of that path.

## How far to trust it

Every prose statement carries a `path:line` in the pinned tree together with its complete gate — which control keys and values, which routing method, standalone or coupled, which code path. Two grades are used: **read in source** covers almost everything, and **confirmed in the sample control files** marks a control-file claim also checked there. There is no third grade, because **nothing was verified against model output**. Where the in-repo documentation, a code comment and the code disagree, the pack states what the code does and names the disagreement — five such cases are recorded in [sources.md](sources.md), and the shipped sample control file is itself not runnable as it stands. The catalogs are mechanical and not exhaustive; `pack.yaml`'s `known_gaps` lists what they could not resolve.

## Regenerate and validate

```
tools/extract_pack.py --pack mizuroute all --source-root <mizuRoute checkout> --out-dir catalogs
tools/hcm_check.py pack-info --pack mizuroute
```
The first rebuilds the catalogs from the pinned checkout, the second prints the declared files, known gaps and curated fact counts. The prose is hand-maintained.
