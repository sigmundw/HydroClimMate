# VIC — process map

Source root VIC `14a371a8` (5.1.0); `path:line` relative to it. **run** = `vic/vic_run/src`, **sh** = `vic/drivers/shared_all/src`, **cl** = `vic/drivers/classic/src`, **im** = `vic/drivers/image/src`, **shim** = `vic/drivers/shared_image/src`, `vic_def.h` = `vic/vic_run/include/vic_def.h`. Executable defaults: the initialisers at `sh/initialize_options.c:20-82`. Names, values and units: `tools/hcm_lookup.py --pack vic <NAME>` — this file gives gates, not tables.

## Drivers and time stepping

Question: what is a step, and how is output framed. Keys: the four step counts (`ATMOS_STEPS_PER_DAY` classic only — image calls it *not a valid option for this driver*, `im/get_global_param.c:524-527`), `NLAYER`, `NODES`, `CALENDAR`, and the output block `OUTFILE`/`OUTVAR`/`AGGFREQ`/`COMPRESS`/`OUT_FORMAT`, plus image-only `HISTFREQ`. Enforced at `cl/get_global_param.c:692-864`, parsed at `cl/parse_output_info.c:76-192`. Each count must be 4..1440 — only the model step may also be 1 — and **above 24 must be an exact multiple of 24**, the fatal test `x % 24 != 0`, so 48 is legal and 36 is not (`:715-720,753-758,785-790,824-829`). The snow step must equal the model step unless that is daily (`:731-736`); runoff and atmos must be multiples of the model step, atmos **also** of the snow step, defaulting to 24 if absent (`:800-851`). An output stream is an `OUTFILE <prefix>` line plus its own `AGGFREQ`, `COMPRESS`, `OUT_FORMAT` and `OUTVAR <NAME> [format] [type] [mult] [aggtype]` lines; with none, VIC builds a default set (`sh/set_output_defaults.c`).
- `surface_fluxes` runs the sub-step loop **only when there is snow** — `if (snow->swq > 0 || snow->snow_canopy > 0 || force->snowflag[NR])` it loops `NF = snow/model` times at the snow step, else once at the model step using slot `NR` (`run/surface_fluxes.c:258-269`), so snow-free periods cost one pass whatever the snow step says. `runoff()` then runs **once per model step** on the summed precipitation (`:1078-1081`); its own step count is a loop *inside* it.

## Forcing

Question: what must the forcing contain, in what units. Keys `FORCING1`/`FORCING2`, `FORCE_TYPE`, plus classic-only `FORCE_FORMAT`, `FORCE_ENDIAN`, `FORCE_STEPS_PER_DAY`. Fifteen type names exist, `SKIP` among them; seven are required by name (`cl/get_force_type.c:41-104`, `cl/vic_force.c:43-63`). Units, file → conversion → internal: air temperature **C**, precipitation **mm over the forcing step**, radiation W/m2 and wind m/s pass unscaled; pressure and vapour pressure are **kPa** on file, multiplied by `PA_PER_KPA` to Pa in both drivers (`cl/vic_force.c:116-118`, `im/vic_force.c:397-399`). `CATM` is **not** ppm despite its comment: nothing scales it on read and the output divides by 1e-6, so the file holds ppm x 1e-6 (`cl/vic_force.c:147`, `sh/put_data.c:137`); `CHANNEL_IN`, documented m3, is read as a depth in mm over the cell (`run/vic_run.c:418`).
- **VIC 5.1.0 disaggregates nothing** (MTCLIM removed): the forcing step must equal `SNOW_STEPS_PER_DAY` and a sub-daily forcing the model step too (`cl/get_global_param.c:977-980`, `cl/read_atmos_data.c:58-65`). The band temperature and precipitation factors are applied **not** on read but inside the band loop (`run/surface_fluxes.c:358-359`).

## Vegetation tiles, canopy and ET

Question: who transpires and who evaporates. Keys `VEGLIB`, `VEGPARAM`, `ROOT_ZONES`, `LAI_SRC`/`ALB_SRC`/`FCAN_SRC` and their presence flags, `SHARE_LAYER_MOIST`, `RC_MODE`. Answers: `OUT_EVAP`, `OUT_TRANSP_VEG`, `OUT_EVAP_BARE`, `OUT_PET`. `penman()` returns **mm/day**; every caller rescales by `delta_t / CONST_CDAY` (`run/penman.c:203-204`). Transpiration uses the Jarvis canopy resistance unless `CARBON` is true **and** `RC_MODE == RC_PHOTO` (`run/canopy_evap.c:275,376`); with `CARBON` false the parser resets it to `RC_JARVIS` **with a warning** (`cl/get_global_param.c:1139-1145`). Bare-soil evaporation is ARNO on **layer 0 only**, weighted `(1 - fcanopy)`; canopy terms are weighted `fcanopy`, and a tile is vegetated only if `fcanopy > 0 && LAI > 0` (`run/func_surf_energy_bal.c:732-760`, `run/calc_surf_energy_bal.c:145-155`).
- Only the model-step slot `NR` of the vegetation series reaches the tiles, so LAI, albedo and fcanopy are constant across snow sub-steps and bands, and are a **monthly step function** unless read from a veg-history forcing (`sh/update_step_vars.c:36-44`).

## Energy balance modes

Question: how is the surface temperature obtained, and what does it cost. Keys `FULL_ENERGY`, `QUICK_FLUX`, `QUICK_SOLVE`, `IMPLICIT`, `EXP_TRANS`, `NOFLUX`, `CLOSE_ENERGY`, `FROZEN_SOIL`, `GRND_FLUX_TYPE`, `TFALLBACK`. Answers: `OUT_SURF_TEMP`, `OUT_SENSIBLE`, `OUT_LATENT`, `OUT_GRND_FLUX`, `OUT_ENERGY_ERROR`. The switches are validated together at `cl/get_global_param.c:1239-1298` ([failures.md](failures.md)); node spacing is three fixed nodes under `QUICK_FLUX`, linear otherwise, exponential under `EXP_TRANS` (`cl/read_soilparam.c:709-800`). Neither the canopy-air solve nor the ground/canopy iteration reports non-convergence, and `TFALLBACK` (default true) silently reuses the previous surface temperature when `root_brent` fails (`run/surface_fluxes.c:714-720`, `run/calc_surf_energy_bal.c:310-315`).
- **`FULL_ENERGY FALSE` does not skip the energy code.** It sets `Tsurf = Tair` instead of solving (`run/calc_surf_energy_bal.c:246,522-524`); `solve_surf_energy_bal()` still runs, so ground heat flux, turbulent fluxes, ET and the thermal profile are evaluated at air temperature.

## Snow

Question: where the snow is and when it melts. Keys `SNOW_DENSITY`, `SNOW_BAND`, `BLOWING` and its sub-options, `SPATIAL_SNOW`, `MAX_SNOW_ALBEDO`, plus the constants-file rain/snow temperatures. Answers: `OUT_SWE`, `OUT_SNOW_DEPTH`, `OUT_SNOW_MELT` and the `*_BAND` set.
- The ground pack is **two layers split by water equivalent, not depth**: the surface layer holds up to `SNOW_MAX_SURFACE_SWE` (0.125 m w.e.), the pack layer is the remainder and is absent below it, its temperature then exactly 0.0 (`run/snow_melt.c:91-100,432-462`). Canopy snow exists **only on overstory classes**, blowing snow only where `!overstory && BLOWING && swq > 0` (`run/solve_snow.c:161-224`, `run/surface_fluxes.c:416-437`).

## Soil moisture, infiltration, runoff and baseflow

Question: where does the water go. Keys `BASEFLOW`, `RUNOFF_STEPS_PER_DAY`, `ORGANIC_FRACT`, `BULK_DENSITY_COMB`. Answers: `OUT_RUNOFF`, `OUT_BASEFLOW`, `OUT_SOIL_MOIST`, `OUT_ZWT`, `OUT_WATER_ERROR`. Layer 0 is the surface layer, baseflow leaves the bottom layer only, and the infiltration curve uses layers `0 .. Nlayer-2` combined (`run/runoff.c:423-464`), never the bottom one. `BASEFLOW NIJSSEN2001` adds no column and is converted in place (`cl/read_soilparam.c:698-707`, `shim/vic_init.c:818-829`); an unrecognised value is fatal in image but falls back to `ARNO` silently in classic (`im/get_global_param.c:392-403` vs `cl/get_global_param.c:412-420`).
- **The curve is evaluated once per model step, not per runoff sub-step.** That estimate is divided by the sub-step count and removed from layer 0 only (`run/runoff.c:147-153,196-201`); the loop refines drainage and baseflow, and further runoff is saturation excess cascading **upward** out of a full column (`:226-230,322-327`). `Ksat` and `Dsmax` are mm/day on file, divided by the runoff step count inside (`:68-69,161`); runoff and baseflow leave in **mm per model step** (`vic_def.h:795-796`).

## Lakes and wetlands

Question: is there open water. Keys `LAKES` (which names the lake parameter file), `LAKE_PROFILE`, `LAKE_NODES`, `RESOLUTION`, `EQUAL_AREA` and the optional `CHANNEL_IN` forcing, their combinations validated at `cl/get_global_param.c:1306-1335`. Answers: the `OUT_LAKE_*` family and `OUT_SURFSTOR`.
- The lake occupies one tile, band count forced to 1, land fraction scaled by `(1 - lakefrac)` (`run/vic_run.c:135-160`). Cell area is read only when `LAKES` is true — from `RESOLUTION`/`EQUAL_AREA` in classic (`cl/compute_cell_area.c:27-48`), the domain `area` in image (`shim/vic_init.c:1531`) — and does more than scale reports: it builds the basin depth-area table and its fractions (`sh/compute_lake_params.c:30,46,57`) and converts runoff, baseflow and `CHANNEL_IN` into the lake's m3 inflow (`run/vic_run.c:414-419`), so a wrong `RESOLUTION` changes the lake **simulation**, not just the `OUT_LAKE_*` numbers.

## Carbon

Question: is photosynthesis on. Keys `CARBON`, `VEGLIB_PHOTO`, `RC_MODE`, `CANOPY_LAYERS` and the `CATM`, `FDIR`, `PAR` forcings. Answers: `OUT_GPP`, `OUT_NPP`, `OUT_RHET`, `OUT_NEE`. `CARBON TRUE` **requires** `VEGLIB_PHOTO TRUE` and the veg library's carbon block (`cl/get_global_param.c:1146-1153`), and adds a photosynthesis solution per canopy layer in every sub-step (`run/surface_fluxes.c:725-782`).
- `OUT_RHET` arrives in gC/m2/day and is **multiplied** by `dt_sec / SEC_PER_DAY`, so the written value is gC/m2 over the model step although its metadata says `g m-2 d-1` and the comment there claims the opposite conversion. `OUT_NPP` stays `g m-2 s-1`, so `OUT_NEE = OUT_NPP - OUT_RHET` subtracts a per-step amount from a per-second rate (`sh/put_data.c:508-509`, `sh/history_metadata.c:1188,1204,1212`).

## Routing

Question: is there river routing. **Classic: none** — no routing source, call or make variable under `vic/drivers/classic`. **Image: a build-time extension.** `vic/drivers/image/Makefile:22-31` sets `ROUT` to `rout_stub` (the default, four empty function bodies at `vic/extensions/rout_stub/src/rout.c:12-39`) or `rout_rvic`, which sums `OUT_RUNOFF + OUT_BASEFLOW` per active cell, gathers to the root task, convolves against a unit hydrograph from the `ROUT_PARAM` NetCDF file and scatters it into `OUT_DISCHARGE` (`vic/extensions/rout_rvic/src/rout_run.c:53-73`).
- Discharge is written **only at outlet cells**, in m3/s, and the conversion uses the outlet cell's area alone, so the unit hydrograph must carry the source weighting (`rout_convolution.c:57-62`).

## State files and restarts

Question: how do I continue a run. Keys `INIT_STATE`, `SAVE_STATE`, `STATENAME`, the four `STATE*` date fields and `STATE_FORMAT`. The state date is the **end** of the step matching those four fields exactly (`im/check_save_state_flag.c:24-40`). Classic writes `<STATENAME>_YYYYMMDD_SSSSS`, ASCII by default, one block per cell: a `cellnum Nveg Nbands` header, in `BINARY` an `int` byte count for the rest of the cell (`:66-122`), the node thicknesses and depths, then one record per (veg, band) pair opening with its own index pair (`cl/write_model_state.c:55-60,122-148,157-161`). Image writes `<STATENAME>.YYYYMMDD_SSSSS.nc`, variables veg-major and grid-last — `(veg_class, snow_band, nlayer, y, x)` — with `soil_node` where history uses `node` (`shim/vic_store.c:51-54,1362-1390,1663`).
- On restore, classic compares **only** the layer and node counts (`cl/check_state_file.c:58-67`), image the grid, five subgrid dimensions, every coordinate and the node geometry (`shim/vic_restore.c:910-1100`) — **neither compares the state file's time stamp with the run's start date, nor any option**.

## Parameters and calibration handles

Question: what can be tuned and where the code reads it. The soil table carries the baseflow and per-layer hydraulic sets, densities, moistures and cell scalars; the veg library the resistance and monthly canopy blocks; the veg parameter file tile fractions and roots. **Column orders, NetCDF names, units and defaults are in the catalogs, not here.** Scalar constants are overridable in the `CONSTANTS` file (`sh/get_parameters.c`), where `SNOW_MAX_SNOW_TEMP`, `SNOW_MIN_RAIN_TEMP` and `LAPSE_RATE` live. An image parameter file also needs two variables read outside `vic_init.c`: an `NC_INT` `run_cell`, which defines the active cells, and `Nveg` (`shim/get_global_domain.c:57-61,331`).
- The classic reader enforces the code's bounds — infiltration exponent > 0, Brooks-Corey exponent >= 3.0, quartz in [0,1] under `FULL_ENERGY`, bulk below particle density, wilting point between residual and critical moisture (`cl/read_soilparam.c:99-339,645-659`) — where image checks only depth, ordering and four values (`shim/vic_init.c:746-813`), so a set classic rejects runs silently.
