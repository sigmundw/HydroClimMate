# Model pack structured layers — schema

A pack's structured layers are confronted by `tools/hcm_check.py`/`tools/hcm_lookup.py` against actual files; a declaration is not proof. See [core.md](../core.md#local-model-knowledge). No acceptance thresholds here — those stay in the project's experiment record.

## Two depths

A pack declares its `depth` in its manifest (`pack.yaml`, field `depth`):

- **`outline`** (the five packs `ctsm`, `issm`, `modflow`, `rbm`, `wrf-urban`). Orientation from public documentation, not source-verified. Prose only: five Markdown files (`overview.md`/`execution.md`/`outputs.md`/`pitfalls.md`/`sources.md`) plus `pack.yaml`. No `curated/` or `catalogs/` directory, and no machine-readable declaration for `hcm_check.py --pack`/`hcm_lookup.py` to confront — both print a one-line note (`outline pack: no machine-readable declarations`) instead.
- **`reference`** (`hrldas-noahmp`, `vic`, `mizuroute`). Source-extracted catalogs, line-cited against a pinned checkout, cross-checked against real output where any exists — `vic` has no reachable model output, only the pinned source and the public VIC sample inputs (see the evidence grades below). A card + process map + symptom-indexed failure list + bounded recipes + version anchor, backed by **generated catalogs** (`catalogs/`) mechanically extracted from a pinned source tree, plus hand-authored **curated layers** (`curated/`). Each `depth: reference` pack may also carry a top-level `README.md`: a short, human-facing entry point (what the model is, what the pack covers and at which version, how a person and an agent use it, file map, what is verified and how, limits, regenerate/validate, citation and credit) — capped at 5120 bytes, distinct from `card.md`'s dense per-fact orientation for an agent already acting. Agents are **not** routed to `README.md` (`models/index.md`/`core.md` never link to it); it exists for a person browsing the pack directory.

## `pack.yaml` (manifest, every depth)

`{pack, title, depth, version_scope, prose: [{file, purpose}]}`, plus for `depth: reference` only: `{catalogs: {generated_from, regenerate, validate}, curated: [{file, purpose}], known_gaps: [...]}`. `prose`/`curated` each name every prose/curated file the pack actually has, with a purpose stated in 12 words or fewer — pack.yaml states what the pack IS, not why it is that way; a longer rationale belongs in the cited prose file itself, not the manifest. `catalogs` names the fixed commands that regenerate and validate the generated data catalogs (see below), and may additionally carry `files: [{file, purpose}]`, naming every generated catalog file the pack has with the same short purpose — the two machine-only files included, so the manifest lists what a reader would find in the directory rather than leaving the generated half undeclared. An optional `checks: {…}` block names a command the pack offers for checking a user's own input against those catalogs before a run, with a `covers` line stating exactly what it does and does not evaluate — a pack states this only when such a command exists for it. `known_gaps` is a short list of plain-language facts about what the mechanical extraction or validation did not reach — not prose, not a justification, just what remains unestablished.

## Curated layers (`depth: reference` only, under `curated/`)

Fixed filenames, all optional (present only if the pack's prose/catalogs do not already state everything the layer would add): `curated/interface.yaml` (data interface: files, inputs, outputs), `curated/switches.yaml` (declared switch effects), `curated/checks.yaml` (detectable checks), `curated/workflows.yaml` (common task sequences). Header comment: one line, `Hand-maintained. <purpose>.`

**Every structured fact** (not a container) in a curated layer carries:

- `source` — a source id in this pack's `sources.md`, or `null` if uncited.
- `scope` — model/driver/version string, or `"unspecified in the pack"`.
- `basis` — `source_read` | `observed_in_output` | `both` | `unverified`.
- `from` — `{"file", "anchor"}` pointing at the prose sentence it came from.
- `confirmed_against` — a short hash (`tools/_anchor_hash.py`) of the `from.anchor` paragraph's text at the time a person last confirmed the fact still agrees with that prose.

`evals/check_knowledge.py` recomputes each fact's paragraph hash and fails if it does not match — a prose correction changes the paragraph's text, which is exactly what should force every curated fact citing it to be re-read and re-confirmed, not silently kept. After confirming (or fixing) each flagged fact by hand, run `tools/refresh_confirmed_against.py --pack <pack>` once to update the stored hashes; the tool never adjusts a fact's own claim, only the hash. The hash is whitespace-insensitive, so reflowing a paragraph's line wrapping alone never forces a re-confirmation.

`basis: unverified` can never yield a VERIFIED/CONSISTENT check verdict. `basis: both` (source-read AND separately confirmed against real output) sits alongside the catalogs' `evidence` field of the same three-plus-one shape (see below); otherwise a curated-layer fact is `source_read`, `observed_in_output` or `unverified` singly. Where a generated catalog entry already carries a fact (e.g. a variable's units/kind/fill — see below), the curated layer references that catalog entry instead of restating it.

`curated/interface.yaml`: `{pack, files: [...], inputs: [...], outputs: [...]}`, each a flat list of facts. `files` entries: `{file_kind, statement, ...4 keys}` — role/naming/record-structure/time-stamp meaning, only as stated. `inputs`/`outputs` entries: `{variable, aspect, statement, ...4 keys}`; `aspect` ∈ `units|kind|time_stamp_convention|fill|dimension_order|valid_support|identity|forcing_categories|...`; `kind` ∈ `instantaneous|accumulated_since_start|interval_mean|state`. `fill` facts may add `attribute_declared` (bool) and `known_raw_value_order` (number). `accumulation-and-fill --pack` reads `outputs` facts for `--var`; `describe --pack --file` reads both `inputs` and `outputs` for every variable actually in the file, printing NO DECLARATION where silent — expected for most variables, and for every catalog-only fact (use `hcm_lookup.py --pack <p> <NAME>` for those instead).

`curated/switches.yaml`: `{pack, switches: [{name, structural_change, exchanged_fields, untouched_fields, expected_scaling_variable}]}` — each of the four is a fact object (`{statement, ...4 keys}`, `exchanged_fields`/`untouched_fields` also carry a `fields` list) or absent if not stated. `paired-response --switch` reads this to flag which compared variables are exchanged, untouched, or unmentioned, and to hint `--control-var` (never applied silently).

`curated/checks.yaml`: `{pack, checks: [{id, detect?}]}`. `id` names the matching heading's anchor slug in this pack's symptom-indexed prose (`failures.md` for a `depth: reference` pack) — every `id` must be an anchor that heading list actually has, but the reverse is not required: `checks.yaml` holds one entry per failure this pack can automate a check for, not a restatement of the whole symptom list. `detect` (present only if automatable): `{check, ...params, what_counts, source, scope, basis, from}`; `check` must name an existing `hcm_check.py` subcommand.

`curated/workflows.yaml`: `{pack, workflows: [{name, steps: [{step, what_is_done, must_establish, check, ...4 keys}]}]}`, only for sequences the pack's prose already describes. A step names the evidence to produce (`must_establish`) and, if one exists, an observation or `hcm_check.py` subcommand that would establish it (`check`, nullable) — never a gate the executing agent certifies for itself as passed.

## `catalogs/index.json` (generated key index — always JSON, `depth: reference` only)

`{pack, generated_by, entries: [{name, kind: file|input|output|switch|variable, declared_in, from, related_switches, related_checks}]}`, built by `tools/build_index.py <pack> --write` from `curated/interface.yaml`, `curated/switches.yaml` and `curated/checks.yaml`. Never hand-edit: the validator checks the committed file equals a fresh build. `hcm_check.py lookup --pack P NAME` prints an entry. This is a *machine-only* file (a build artifact, not prose a person reads for its own sake) and so stays JSON — see "YAML subset" below. `build_index.py` refuses to build one for a `depth: outline` pack.

## Self-test fixtures (`evals/<pack>/selftest.yaml`)
`{pack, cases: [{pitfall_id, faulty: {...fixture spec}, clean: {...fixture spec}}]}`, one case per `curated/checks.yaml` entry with a `detect` stanza. Lives under `evals/`, not the pack directory, since it is contributor test data, not pack content an agent reads. `tools/selftest.py --packs` builds the fixtures on the fly (none stored in the repo) and asserts FIRED on faulty / QUIET on clean.

## `depth: reference`: catalogs, reading order, and the YAML subset

### Reading order (what an agent should actually do)

For a `depth: reference` pack, read **`card.md` only** as the must-read file (hard-capped, see below). From there:

1. Any variable/option/parameter/constant name → `tools/hcm_lookup.py --pack <pack> <NAME>` (queries the catalogs; never read a `catalogs/*.yaml` file wholesale — they exist to be queried, not read).
2. A symptom ("my totals are off", "the switch did nothing") → `failures.md`, indexed by symptom.
3. "How does this process work / what module implements it" → `processes.md`, a question → switch → module → variable map.
4. A bounded task with a known cost ("period total", "daily mean", "paired difference") → `recipes.md`.
5. Whether a checkout/output matches this pack's pin → `version.md`.
6. Provenance / what backs a claim → `sources.md` (ids `L0`-`L6`, plus floating `H*` records kept only where a curated-layer fact still cites one).

`models/index.md` and `core.md`'s local-model-knowledge paragraph state this same order for the agent.

### Catalogs (generated, never hand-edited)

`catalogs/*.yaml` (`outputs`, `restart`, `forcing`, `setup`, `namelist`, `physics_options`, `parameters`, `constants`, `urban_path`) are produced by `tools/extract_pack.py` directly from the pinned source tree — never hand-typed — and re-derived by running the extractor again (diff against the committed file is the drift check, same discipline `catalogs/index.json` already used). Every catalog file:
- `{"pack", "catalog", "generator", "generator_version", "scope", "count", <catalog-specific list key>}`.
- `generator` names the exact `extract_pack.py` subcommand that produced it.
- `scope` is the fixed string `"HRLDAS <hrldas-commit> + noahmp <noahmp-commit>"` for this pack's pinned pair — see `catalogs/MANIFEST.json` for the exact hashes, and [version.md](hrldas-noahmp/version.md) for how the commit is pinned. The canonical short form for a commit anywhere in this pack (prose, catalogs, `sources.md`) is `git rev-parse --short=8` in the pinned checkout — 8 hex characters, e.g. `d9f5b205`/`9fbe6724` — not `git describe`'s own 7-character abbreviation, which is still quoted verbatim where the text is literally reporting what `git describe` printed (`version.md`, `sources.md#l0`).

Every extracted **fact** (a dict describing one variable/key/parameter/ constant/observation) carries:
- `where` = `{"file", "line", "commit"}` (a pack whose source is a single repository, e.g. `vic`, adds a fourth key, `"driver"` ∈ `classic | image | both` — see that pack's own catalogs for the exact shape). `file` is relative to the source root passed to `--source-root`; `commit` is `"hrldas@<hash>"`/`"noahmp@<hash>"`/`"vic@<hash>"` depending which repo the file belongs to.
- `evidence` ∈ `source_read | observed_in_output | both | confirmed_in_sample_input`. Every fact starts `source_read` (produced by parsing source only). `tools/validate_catalogs.py`, run against a real LDASOUT/RESTART/LDASIN file, upgrades matched, non-conflicting facts to `both` **in place**, deterministically: given the same source tree and the same real files, `extract_pack.py all` followed by `validate_catalogs.py --apply` reproduces the committed catalogs byte-identical (verified; see `catalogs/MANIFEST.json`'s `validation` field). It never invents `observed_in_output` alone, since these catalogs are never built from output-reading alone. `confirmed_in_sample_input` is a separate, narrower upgrade for a pack with no reachable model *output* at all (e.g. `vic`, whose pinned checkout carries only public sample *inputs*, not runs): `tools/validate_catalogs.py --pack vic --apply` upgrades an input-format fact (a global-parameter key the sample file actually uses, an input NetCDF variable name/dims/units the sample parameter/domain/forcing files actually declare) from `source_read` to `confirmed_in_sample_input` when the public sample data agrees; nothing in such a pack may ever carry `observed_in_output` or `both`, since no output exists to observe against — SCHEMA.md's own catalog-manifest `validation` field states this plainly for that pack, and its `pack.yaml`'s `known_gaps` says so too.
- `scope` — the same pinned commit string as the catalog manifest (a pack pinned to one repository only names that one commit, plus its own sample-data commit where applicable, rather than a commit *pair*).

This reuses `where`/`evidence`/`scope` rather than the curated layers' `source`/`basis`/`from`, because catalog facts point at *upstream model source*, so they need a file:line:commit, not a `sources.md` id.

**Per-file shape** (see each file's own header comment for the exact regeneration command): `catalogs/outputs.yaml` — LDASOUT variables from `add_to_output(...)` calls, each with `name`, `driver_array`, `description`, `units`, `dimensionality`, `dim_order` (source-declared Fortran order — real files report the **reverse**, confirmed by the validator as the expected case, not a discrepancy), `gating`, `kind`, `kind_evidence`, `fill_note`. `catalogs/restart.yaml` — same shape for `add_to_restart(...)`; description/ units are `null` (absent from source, not guessed) since those call sites never pass them. `catalogs/forcing.yaml` — LDASIN roles, each with its `forcing_name_*` namelist rename key and whether the read is required. `catalogs/setup.yaml` — HRLDAS setup-file fields. `catalogs/namelist.yaml` — every `NOAHLSM_OFFLINE` key, cross-referenced against `README.namelist`. `catalogs/physics_options.yaml` — namelist key → `IOPT_*` → internal name → dispatch table, for the options that route to a differently-named subroutine (most physics options branch inline instead — a real finding about this codebase, not a shortfall; see the file's own scope note). `catalogs/parameters.yaml` — every `NoahmpTable.TBL`/`URBPARM*.TBL` group and key. `catalogs/constants.yaml` — `ConstantDefineMod.F90`'s constants. `catalogs/urban_path.yaml` — the mechanical urban-path facts, derived by regex from the actual assignment lines. `catalogs/MANIFEST.json` — `{pack, generator, generator_version, scope, source_commits, files: {filename: {count, sha256}}, validation}` (machine-only, stays JSON — see below). `validation`, when present, is `validate_catalogs.py`'s condensed report from its last run against real files: counts only, no paths or run identifiers (see the field's own `note`).

Regeneration:
```
python3 tools/extract_pack.py all --source-root <pinned-checkout> \
    --out-dir hydroclimmate/references/models/hrldas-noahmp/catalogs
python3 tools/validate_catalogs.py \
    --pack-dir hydroclimmate/references/models/hrldas-noahmp \
    --ldasout <one .LDASOUT_DOMAIN1> --restart <one RESTART.*> --ldasin <one .LDASIN_DOMAIN1> \
    --check-kind-sample --apply
```

**Known gaps** (mechanical extraction could not reach these; stated, not hidden): `kind` for the variables/parameters whose accumulate/reset logic lives inside `noahmp/src/*.F90` under local variable names classify_kind cannot trace (or, for the MMF groundwater family, under a local dummy argument name that does not textually match the `NoahmpIO%` field name — see `curated/kinds_overlay.yaml` below) is `state_or_instantaneous` or `undetermined`, not guessed further at the generator level. `physics_options.yaml` covers every namelist option `ConfigVarInTransferMod.F90` maps to an internal `Opt*`/`SF_URBAN_PHYSICS` field (27 at this commit); a value present in `readme_values` but absent from `code_branches` can mean the value is genuinely unhandled, OR that its gate is relational (`>`, `/=`) rather than a literal `==N` the mechanical scan matches — the two must not be read alike, and `curated/options_overlay.yaml` records which is which for the cases checked so far. `namelist.yaml`'s `allowed_values` is empty for keys whose `README.namelist` entry doesn't use the recognized comment shape. Land-use/soil class names are only populated for table groups using the `! N: Name` comment convention.

**`mizuroute`'s own catalog set** (nine files, one pinned repository): `catalogs/control_keys.yaml` (every `<key>` `read_control.f90` matches, with the declaration it assigns to, its `requiredness` — derived from whether `public_var.f90` initialises it to one of that module's own missing-value sentinels, not from a comment — its `allowed_values`, and the parser's own rejection message; plus the lists `post_parse_constraints`, `documented_but_not_parsed` and `in_sample_but_not_parsed`), `routing_methods.yaml`, `network_inputs.yaml`, `outputs.yaml`, `restart.yaml`, `parameters.yaml`, `constants.yaml`, `parallelism.yaml` and `build.yaml`. Three shape points generalise from it. First, each of its catalogs names its own main list key and entry-kind label in the file itself (`entries_key`, `entry_kind`) instead of relying on a table inside a tool, which is how `tools/hcm_lookup.py` indexes and labels a pack whose catalog stems it has never seen. Second, its `where` carries a fourth key, `runmode` ∈ `standalone | cesm-coupling | both` — the run-mode counterpart of `vic`'s `driver` — and a `where` nested inside an already-graded record (the line a variable is forced off at, the line a method names a parameter at) is one more citation of that same fact, so it carries no `evidence` of its own. Third, an output variable's `kind` is a closed vocabulary of its own: `interval_mean`, `instantaneous_end_of_interval`, `interval_sum`, `undetermined`, derived from what `histVars_data.f90` does to the variable's buffer in `aggregate()` and `finalize()`. This pack's only reachable model data are the two sample control files inside the pinned checkout, so there is nothing to point `validate_catalogs.py` at from outside: its `catalogs/MANIFEST.json` `validation` field is produced by `tools/extract_pack.py --pack mizuroute all` in the same deterministic pass (an optional `VALIDATION(root)` hook on the pack's extractor module; a module without one leaves the manifest exactly as before), and a control key one of those two files uses is graded `confirmed_in_sample_input` there and then. Its curated layer is a single `curated/disagreements_overlay.yaml` (below).

### Curated overlays (hand-authored, never generated)

`curated/kinds_overlay.yaml` and `curated/options_overlay.yaml` sit beside the other curated layers, but are never touched by `extract_pack.py` and never asserted equal to a fresh build (`evals/check_knowledge.py`'s `check_catalogs_fresh_build` only iterates the files a fresh `extract_pack.py all` actually produces, which excludes both). Both declare `curated: true` and use the curated-layer citation shape (`where`, `reset_where`, `evidence`, `scope`) rather than being re-derived from a regex pass — the judgement call a mechanical pass cannot make safely is exactly what they exist to hold, always with a citation, re-verified against source rather than merely transcribed.

`curated/kinds_overlay.yaml` — `{pack, catalog: "kinds_overlay", curated: true, scope, count, rows: [{variable, true_kind, where, reset_where?, note?, sampling_note?, units_note?, gate?, updated_when?, evidence, scope}]}`. `variable` must name a real entry in `catalogs/outputs.yaml` (checked by `evals/check_knowledge.py`). `gate` answers "when is this WRITTEN" (often unconditional, e.g. every record once `output_timestep>0`); `updated_when`, where present, separately answers "under which option value(s) does this field's VALUE actually change" — a field can be written every record while its value stays frozen at an initial/restart value for every option except a handful (`ZWT`/`WA`/`WT` are the pack's own example: written unconditionally, but only live under specific `subsurface_runoff_option` values — see `hcm_lookup.py`'s "UPDATED WHEN" line). Conflating the two is the trap this field exists to prevent. `true_kind` is a **closed vocabulary**, one of:
- `state` — a prognostic or diagnostic state, valid at the record's instant; never accumulated.
- `static` — does not change over the run (a land-use/soil category, a fixed level height).
- `instantaneous_rate` — a flux/rate (W/m2, mm/s) at the end of the record's step; integrates correctly against the output interval.
- `per_model_timestep_depth` — a depth computed fresh each `NOAH_TIMESTEP` and written as-is; summing records over the output interval over-counts unless corrected by `OUTPUT_TIMESTEP / NOAH_TIMESTEP` (`RAINRATE`, `PONDING`).
- `per_soil_timestep_energy` — an energy/flux quantity valid for exactly one `SOIL_TIMESTEP`, not since-start (`EFLXB`).
- `accumulated_since_start` — accumulates since run start or the resumed restart; monotone barring a documented cap; difference two records for a period total.
- `accumulated_reset_each_soil_step` — accumulates within one soil timestep and is zeroed the step after (the `ACC_*` family).
- `accumulated_reset_each_mmf_call` — accumulates within one MMF (groundwater) call and is zeroed at the next call (`DEEPRECH`).
- `per_mmf_call_depth` — a depth in metres valid for one MMF call only, not a rate and not since-start (`QRF`/`QSPRING`/`QLAT`).
- `layer_integrated_state` — a state formed by summing over snow/soil layers within one call, not accumulated over time (`SOILENERGY`, `SNOWENERGY`).
- `diagnostic` — a per-record diagnostic that is not itself a physical flux or state in the usual sense (a fraction, a ratio, a value that can be `undefined_real` outside its valid condition).

`curated/options_overlay.yaml` — `{pack, catalog: "options_overlay", curated: true, scope, count, rows: [{internal_option_name, namelist_key, kind, value, note, where, evidence, scope}], note}`. `internal_option_name` must name a real entry in `catalogs/physics_options.yaml`. `kind` is free text describing what the row is for (e.g. `"readme_value_with_no_code_branch"`, `"value_scheme_note"`) — this file is a running list of specific cross-checks, not itself a closed-vocabulary catalog; its own `note` states how much of `physics_options.yaml` it covers (deliberately not exhaustive — see the file's own `note`). A row may also carry `global_parameter_key` (the configuration-file key the row is about, where the pack has one) and `applies_to: [name, ...]`, a list of catalog entry names the row's statement applies to — that is how a row whose subject is an output variable or a forcing type, and so has no option-struct field to be named by, still reaches `tools/hcm_lookup.py`: the lookup indexes a row under every name it mentions across all three fields, and `evals/check_knowledge.py` asserts every `applies_to` name exists in one of the pack's generated catalogs, so a row can never become silently unreachable. A row that corroborates a prose paragraph additionally carries `from: {file, anchor}` and `confirmed_against` (see the drift guard below).

A pack may hold its curated judgement in an overlay named for what it holds rather than for `options`: `mizuroute/curated/disagreements_overlay.yaml` — `{pack, catalog: "disagreements_overlay", curated: true, scope, count, rows: [{subject, kind, note, where, code_where?, reset_where?, evidence, scope, from?, confirmed_against?}], note}`. `subject` names the catalog entries the row is about (several, comma-separated, where a finding covers a family), `where` cites where the disagreement is *visible* and `code_where` the code that wins; `from`/`confirmed_against` are present exactly on the rows whose finding the pack's own prose also states, and absent on the rest. Every `*_overlay.yaml` file a pack has is picked up by listing the directory, not from a fixed stem list, by `tools/hcm_lookup.py` (which merges a row into every catalog entry its `subject` names), by `tools/refresh_confirmed_against.py`, and by `evals/check_knowledge.py` (which resolves each row's citations against the pinned source when given a source root, and re-checks each `confirmed_against` hash against its prose paragraph).

Both are queried the same way as the generated catalogs: `tools/hcm_lookup.py --pack hrldas-noahmp <NAME>` merges a `kinds_overlay.yaml` row into the catalog entry it names (`true_kind` shown next to the generated `kind`, never silently replacing it) and an `options_overlay.yaml` row into the matching physics option's entry; `--list kind=<true_kind>` lists every overlay row with that kind; `--process <keyword>` lists output variables and physics options whose name or description contains the keyword. `tools/validate_catalogs.py --check-kind-sample` tests the empirical monotonicity/reset sample against a variable's overlay `true_kind` when one exists, not the generated `kind` (which would just re-report the known gap for the ~150 `state_or_instantaneous`/`undetermined` variables the overlay exists to resolve).

### YAML subset

Design choice: use YAML instead of JSON for readability. Every pack layer a person or agent reads (curated layers and catalogs) is YAML. Only **machine-only** files — the generated lookup index (`catalogs/index.json`) and a catalog manifest of hashes, counts and validation summary (`catalogs/MANIFEST.json`) — stay JSON, because nobody is meant to read them for their own sake; they exist to be diffed by a script.

The extractor and every hand-authored curated-layer file emit a **strict simple subset** of YAML, implemented in `tools/_miniyaml.py`:
- block style (`key: value` lines, 2-space indents); no flow style at the top level;
- a block list of mappings (`- key: value` then further indented fields) for the main record list in a file, and for any field whose own value is a list of mappings (e.g. a parameter-table group's `parameters`, a physics option's `values`, a workflow's `steps`) — this nests as deep as the data actually requires; there is no arbitrary depth limit on list-of-mapping nesting, only on mapping-of-mapping nesting (next point);
- scalars: `null`, `true`/`false`, a plain JSON number (floats always keep a decimal point, e.g. `1.0e-08` not `1e-08`, so YAML's implicit float resolver — which does not require a decimal point before matching, unlike JSON — still recognizes it as a float and not a string), or a double-quoted string with JSON-style escaping — strings are **always** double-quoted, never bare or single-quoted;
- **one level of nested block mapping**: a dict field whose own values are all scalars (e.g. `where: {file, line, commit}`) renders as an indented block mapping. A dict with a deeper structure (e.g. `kind_evidence`, whose values are themselves dicts) renders inline instead, as a JSON-compatible flow mapping (`{"key": value, ...}`) — valid YAML, valid JSON, one line;
- short lists of scalars (e.g. `dim_order`, `gating`) render as JSON-compatible flow sequences (`["a", "b"]`), never as a block list, since they are not the main record list;
- no anchors/aliases, no multi-line scalars, no tab characters;
- a leading `# `-comment header: generator, source commits (for generated catalogs), and "do not hand-edit; regenerate with ...".

Because every value that is not itself the start of a nested block is a single line of valid JSON, `tools/_miniyaml.py`'s reader only implements the block/indentation walking itself and delegates every terminal scalar/flow span to the stdlib `json` module — and every file this subset can produce is therefore also ordinary, valid YAML that PyYAML's `yaml.safe_load` loads to the identical Python object. Tools load YAML with PyYAML when importable (`hydroclimmate/tools/_miniyaml.py`'s own `load_file` helper does this), else with `_miniyaml`'s own strict-subset reader; `tools/selftest.py` (no flag, or `--yaml`) asserts the two readers agree on every pack YAML file in the repo, and that `_miniyaml.dump(_miniyaml.load(x))` round-trips.

**Reproducibility of the generated catalogs**: `extract_pack.py all` alone is deterministic given the same source tree (pure `source_read` facts). `validate_catalogs.py --apply` is a second, separately deterministic step given the same source tree and the same real LDASOUT/RESTART/LDASIN files: it only ever upgrades a matched, non-conflicting fact's `evidence` from `source_read` to `both`, and refreshes `catalogs/MANIFEST.json`'s hashes and `validation` field for the files it touched. Running both steps against the pinned source and the same real files reproduces the committed catalogs byte-for-byte (checked directly). `evals/check_knowledge.py --source-root <root>` re-runs `extract_pack.py all` alone and asserts the result is structurally identical to the committed catalogs **modulo `evidence` fields that could only differ `source_read` vs `both`** (it cannot also re-run `validate_catalogs.py`, since that needs real output/restart/forcing files, not just a source root).
